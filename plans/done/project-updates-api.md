## Что мы делаем?

Предоставляем обычным пользователям два REST-метода: список активных проектов и последовательное чтение изменений выбранного проекта. Watchdog опрашивает API от имени пользователя, сохраняет прогресс и передаёт события агенту, который через MCP перечитывает доску и выполняет доступную работу.

Сохраняем Go, SQLite, один серверный процесс и существующие персональные токены. Проект остаётся группировкой на общей доске. Активный проект — проект с `is_archived=false`, независимо от наличия карточек и их этапов.

Используем существующий `GET /api/v1/epics` для активных проектов; добавляем `GET /api/v1/epics/{id}/updates?cursor=...&limit=100`. Новые названия `/projects` и дублирующие MCP tools не требуются. Ленту реализуем доменным сервисом, чтобы транспорт не содержал бизнес-правил.

В объём входят события создания, изменения, архивирования и восстановления проектов и карточек, перемещения карточек, смены проекта, создания комментариев и добавления/удаления вложений. Изменения общих справочников, пользователей и настроек доски в первой версии не входят в ленту; это ограничение явно отражается в документации. Реализация watchdog, запуск Codex CLI, распределение работы и блокировки между агентами — отдельная задача. UI не меняем.

## Для чего мы делаем?

Существующий `board.ListEpics` уже исключает архивные проекты, но REST защищён `RequireSession`, а персональные токены используются отдельно. Для постоянного опроса нужен доступ по токену реального пользователя с правом чтения.

`cards.Activity` возвращает только последние события одной карточки; журнал перемещений использует текущее состояние проекта карточки. Комментарии хранятся отдельно. Эти источники не обеспечивают полную, устойчивую ленту проекта: при переносе карточки нельзя потерять событие для прежнего проекта, а совпадающие временные метки не должны приводить к пропускам. Нужен отдельный последовательный журнал, связанный с мутациями транзакционно.
