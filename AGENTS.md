# AGENTS.md

Этот файл описывает правила работы кодинг-агентов с репозиторием JKB. Он действует для всего проекта.

## Продуктовые границы

- JKB — одна общая Kanban-доска. Проекты — это группировка и фильтр, а не отдельные доски.
- Production-схема состоит из одного Go-процесса, SQLite и локального хранилища файлов. Не вводите PostgreSQL, Redis, S3, очереди или несколько реплик без отдельного архитектурного решения.
- `CONTRACT.md` — источник истины для модели, REST API, MCP tools, ролей и ошибок. Если изменяется контракт, обновите этот файл в том же изменении.
- Не добавляйте скрытую автоматизацию миграций при старте: миграции выполняются явно через `jkb-migrate`.

## Структура

- `cmd/jkb` — HTTP-сервер; `cmd/jkb-admin` — административный CLI; `cmd/jkb-migrate` — миграции.
- `internal/*` — доменные сервисы, HTTP/MCP-адаптеры, SQLite и встроенный frontend.
- `migrations` — версионируемые Goose-миграции.
- `src` — Vue 3 + TypeScript + Pinia + Vue Router; UI опирается на Bulma.
- `plans` — активные планы; завершённые планы перемещаются в `plans/done`.

## Порядок работы

1. Перед изменениями прочитайте затрагиваемый доменный сервис, HTTP/MCP-адаптер, frontend store и тесты. Не делайте выводы только по UI.
2. Проверьте `git status`. Не перезаписывайте, не прячьте и не добавляйте в коммит чужие изменения.
3. Делайте изменения маленькими и проверяемыми. Пишите тест на регрессию, а не только на счастливый сценарий.
4. Не публикуйте ветки, не сливайте их в `master`, не создавайте теги и не выкладывайте образы без явного запроса. Push в `master` автоматически публикует GHCR-образ `latest`.

Если задача пришла через JKB/MCP, сначала вызовите `get_current_user`, затем прочитайте карточку и её комментарии. Перед мутацией перечитайте актуальную `version`; не обходите optimistic locking.

## Backend

- REST и MCP должны вызывать одни и те же доменные сервисы. Не дублируйте бизнес-правила в транспортном слое и не давайте MCP обходить auth, роли, scopes и activity log.
- Мутация карточки и запись `card_activity` должны происходить в одной транзакции.
- Карточки изменяются с `expected_version`. При конфликте возвращайте `card_version_conflict` и актуальную карточку; не перетирайте чужие изменения.
- Для SQLite-записи используйте существующий write-transaction helper. Не держите транзакцию открытой во время файлового или сетевого I/O.
- Новая миграция получает следующий номер и не переписывает уже выпущенные SQL-файлы. Добавьте проверку к `internal/database/migrations_test.go`.
- Не логируйте пароли, cookie, bearer-токены, Authorization headers и тела файлов.

## Frontend

- Сохраняйте Vue Composition API и `<script setup lang="ts">`. Общее состояние доски живёт в Pinia store, а не в разрозненных копиях внутри views.
- Переиспользуйте компоненты из `src/components/ui`. Цвета команд и тегов показывайте через `ColorTag`, чтобы не терять WCAG-контраст.
- Действия в `BaseDialog` помещайте в слот `actions`: базовый компонент сам задаёт интервалы. Не компенсируйте их локальными `ml-*`.
- Позиции карточек приходят как десятичные строки. Сравнивайте их как числа через `compareCardPositions`, а не через `localeCompare`.
- Новая карточка появляется первой. Drag-and-drop работает через SortableJS и передаёт `before_card_id` или `after_card_id`. При ошибке восстанавливайте серверный порядок.
- Сохраняйте keyboard-доступ и ARIA-атрибуты. Для нового UI добавляйте проверку в `src/test/accessibility.test.ts` или рядом с компонентом.

## Проверки

Минимально запустите тесты затронутой области. Перед слиянием или релизом выполните полный набор:

```sh
go test -race ./...
go vet ./...
npm run format
npm run lint
npm run typecheck
npm test
npm run test:a11y
npm run build
```

Если песочница запрещает `httptest` открыть loopback-порт, повторите Go-тесты с явным разрешением; не отключайте интеграционный тест.

Production-сборка Vite очищает `internal/frontend/dist`; не оставляйте удалённым отслеживаемый `internal/frontend/dist/.keep`.

## Локальная проверка

Для проверки именно текущего кода собирайте образ, а не загружайте `latest`:

```sh
docker compose build app
docker compose up -d app
docker compose exec app /usr/local/bin/jkb-migrate up
docker compose restart app
curl --fail http://localhost:8080/health/ready
```

Команды приложения, мигратора и административного CLI в примерах выполняйте через `docker compose exec app` внутри уже работающего контейнера. Не используйте `docker compose run --rm app ...` в развёрнутом стенде: reverse proxy с service discovery через Docker socket может увидеть одноразовый контейнер как экземпляр сервиса и направить на него часть запросов.

Если `8080` занят, задайте другой `JKB_PORT`, не останавливая неизвестный сервис. Миграции изменяют локальный volume; не выполняйте destructive rollback без явного запроса и резервной копии.

## Готовность изменения

Изменение готово, когда:

- поведение покрыто релевантными тестами;
- контракт и документация не расходятся с кодом;
- не нарушены optimistic locking, транзакции, auth и activity log;
- полный набор проверок проходит;
- ручной UI-сценарий проверен для видимого изменения;
- в рабочем дереве нет случайных артефактов сборки, секретов или чужих изменений.
