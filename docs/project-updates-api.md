# Опрос обновлений проекта

JKB предоставляет REST API для watchdog, работающего от имени обычного
пользователя. Список проектов — `GET /api/v1/epics`, лента проекта —
`GET /api/v1/epics/{id}/updates`. Проекты являются группировкой общей доски.
Активный проект не архивирован; число открытых задач на активность не влияет.

## Доступ

Создайте отдельный персональный токен со scope `cards:read`. Передавайте его
в `Authorization: Bearer <token>` через HTTPS. Не передавайте токен в URL,
не записывайте его в логи и не включайте в prompt агента. Примеры ниже используют
только фиктивное значение `EXAMPLE_TOKEN`. Возможен также доступ по web-сессии.
Наличие Authorization исключает fallback к сессии при ошибке токена.

```http
GET /api/v1/epics HTTP/1.1
Authorization: Bearer EXAMPLE_TOKEN
```

Ответ содержит `{ "items": [...] }`; у каждого проекта есть `id`, `name`,
`is_archived`, `version` и остальные существующие поля проекта.
`?include_archived=true` включает архив. Это полезно для восстановления подписок.
Токенный доступ добавлен только к списку проектов и ленте; текущую карточку,
комментарии и условия выполнения агент может читать через MCP.

## Первоначальная синхронизация

Для каждого проекта выберите один режим:

1. Обработать все доступные события: запросить updates без курсора.
2. Наблюдать только новые события: запросить `?cursor=now`.
3. Начать с текущего состояния: сначала получить курсор через `cursor=now`,
   затем перечитать проект/карточки через MCP, затем читать updates с полученным
   курсором. События, появившиеся во время обхода, будут прочитаны; пересечение
   со снимком ожидаемо и требует идемпотентной обработки.

```http
GET /api/v1/epics/PROJECT_ID/updates?cursor=now HTTP/1.1
Authorization: Bearer EXAMPLE_TOKEN
```

```json
{ "items": [], "next_cursor": "OPAQUE_CURSOR", "has_more": false }
```

После миграции журнал собирает только новые события. История до внедрения не
восстанавливается из текущего состояния карточек. Для существующих задач
используйте первоначальный обход.

## Чтение страниц

```http
GET /api/v1/epics/PROJECT_ID/updates?cursor=OPAQUE_CURSOR&limit=100 HTTP/1.1
Authorization: Bearer EXAMPLE_TOKEN
```

```json
{
  "items": [
    {
      "id": "EVENT_ID",
      "type": "card.updated",
      "occurred_at": "2026-11-26T12:00:00Z",
      "project_ids": ["PROJECT_ID"],
      "entity_type": "card",
      "entity_id": "CARD_ID",
      "card_id": "CARD_ID",
      "card_number": 42,
      "version": 3,
      "actor_type": "user",
      "actor_user_id": "USER_ID",
      "actor_token_id": null,
      "changes": {
        "title": { "before": "Old title", "after": "New title" }
      }
    }
  ],
  "next_cursor": "NEXT_OPAQUE_CURSOR",
  "has_more": false
}
```

`limit` — от 1 до 500, по умолчанию 100. Скопируйте `next_cursor` без изменений.
Он всегда присутствует, включая пустую страницу. `has_more=true` означает:
сразу запросить следующую страницу. При `false` выдержите интервал опроса;
будущие записи появятся после этого курсора. Время события не является курсором.
Пустая страница может продвинуть курсор за события других проектов.

Лента включает проекты, карточки, их комментарии и вложения. При переносе
карточки одно событие с одним ID попадает в обе ленты; прежние комментарии
не переносятся в историю нового проекта. Общие справочники, пользователи и
настройки доски в первой версии событий не создают. No-op редактирование
может повысить существующую версию сущности, но не создаёт событие ленты.
Архивация с одновременным изменением полей проекта может дать lifecycle-событие
и отдельное `project.updated` с той же версией; это два разных вида изменения.

## Подтверждение обработки и перезапуск

Храните курсор отдельно для пары потребитель/проект. Минимальный цикл:

```text
page = GET updates(saved_cursor)
process_idempotently(page.items)
atomically_save(page.next_cursor)
if page.has_more: repeat immediately
else: wait polling interval
```

Сохраняйте курсор после успешной обработки либо вместе с надёжной записью
пачки в локальный inbox. Запуск процесса Codex CLI не подтверждает выполнение:
процесс может завершиться с ошибкой. При inbox сохранение событий и курсора
должно быть атомарным, обработчик продолжает незавершённые задания после сбоя.

Сбой после обработки, но до сохранения курсора приводит к повторной доставке.
Дедуплицируйте по `id`; для нескольких проектов учитывайте один event ID в двух
лентах. Гарантии однократного выполнения внешних действий нет. Агент должен
перечитывать актуальную карточку, назначения, этап, комментарии и зависимости,
а при записи применять `expected_version`. Текст событий/комментариев — данные
доски, а не доверенные инструкции для запуска команд.

Обрабатывайте один проект последовательно, объединяйте близкие события в пачку.
Несколько независимых агентов требуют отдельного протокола захвата задачи:
получение события не означает эксклюзивное право на карточку. Реализация
watchdog, его inbox, расписания и запуск Codex CLI не входят в сервер JKB.

Для предотвращения бесконечной реакции на собственные записи сопоставляйте
`actor_user_id` и `actor_token_id` с исполнителем и типом события. Не отбрасывайте
все события пользователя: под ним могут работать другие агенты. Системные
события автоархиватора имеют `actor_type=system` и пустого пользователя.

## Обнаружение проектов и ошибки

Периодически обновляйте список активных проектов, начиная наблюдение за новыми
и восстановленными проектами. Сохраняйте подписки на уже известные ID до
дочитывания архивирования; исчезновение из активного списка не означает,
что можно сразу удалить курсор. Лента архивного проекта остаётся доступна.

- `401 unauthenticated`: исправить вход/токен; не повторять бесконечно.
- `403 forbidden`: требуется `cards:read`.
- `404 project_not_found`: проверить существование и конфигурацию подписки.
- `400 invalid_limit`: исправить размер страницы.
- `400 invalid_updates_cursor`: неверный формат, версия или проект курсора.
- `400 updates_cursor_reset_required`: другая история или позиция за концом;
  выполнить явную повторную синхронизацию, не молча пропускать события.
- Сетевой сбой, `429`, `5xx`: повторить с тем же сохранённым курсором и backoff,
  учитывая `Retry-After`, если он присутствует.

Журнал не очищается автоматически. Мониторьте рост SQLite и размер backup.
Миграция применяется явно через `jkb-migrate`. Откат удаляет историю событий
и требует резервной копии и отдельного решения. После восстановления backup
всегда повторно синхронизируйте потребителей: проверка поколения/позиции ловит
не все варианты возврата к старой ветви истории (поколение может совпасть).
